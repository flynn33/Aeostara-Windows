## Verification report and plan

The candidate baseline `8680b6fc0fd3bef79cc31ed2d61aa7684141062d` has recorded successful native qualification for LEAN and DEVELOPMENT in both Debug and Release. Each configuration executed all six registered CTest targets, including 239 Core, 8 architecture and 13 CLI native tests with zero failures. The remaining targets are `SemanticConformanceTests`, `LifecycleConformanceTests` and `DiagnosticFoundationTests`. These are candidate results, not an assertion that a later source revision or downloaded release has been qualified.

Subsequent focused Development Debug execution ran all 28 `SemanticMappingTests` successfully, including twelve added proofs and regressions. Actual pre-fix runs exposed three terminal-context successes, unnormalized topology generation and two unresolved diagnostic-reference successes. The first registry-negative attempt failed an incorrect preliminary test assertion: `101010101` is compatible with the recognized catalog, although it is not itself valid. That premise was corrected without changing the required registry rejection. Historical failures and the correction remain recorded; the final focused run verifies the corrected tests and guarded provider. This authoring run used a dirty working tree and does not substitute for a clean final-source four-configuration qualification.

`SemanticConformanceTests::calculate` receives input and authority only. Expected properties are compared after evaluation. Its `HARNESS` branch supplies only input from a carrier with renamed fixture metadata and a poisoned assertion value; neither metadata field enters the evaluator arguments. The harness also uses three genuinely shuffled orders and sixteen repeated evaluations. It covers 104 non-execution vectors and independently diagnoses all 512 states against the adopted fixed catalog. `LifecycleConformanceTests` executes the ten controlled lifecycle vectors through actual supplied adapters. The canonical codeword set and recognized-state catalog are separate authorities; the adopted catalog yields two valid, thirty compatible and 480 incompatible states.

## Diagnostics conformance report

Canonical diagnostic construction uses source-bound `RuleReference` values, the ASH taxonomy, stage/disposition evidence and validated roots/parents. Successful provider references resolve through the public transport to retained genuine chains. The provider owns at most 64 chains and 16 MiB, rejects operations needing new chains when exhausted, and does not evict chains already referenced by successful results. The budget test resolves the first successful reference after the sixty-fifth distinct attempt is rejected.

`DiagnosticFoundationTests` checks deterministic canonical envelopes, detection/recovery/containment/terminal chaining, attempted continuation after terminal, orphan parents, wrong rule families and unresolved sources. Native phase tests check actual detection/classification evidence and pinned rule sources. Export tests check redaction, limits, expiry, complete paired output, collision and dishonest/partial writer failures. These collector/export assertions are distinct from frozen DTO/schema and canonical-chain checks.

Required semantic chains and durable business audit remain execution gates. Developer collector failures are measured secondary evidence and do not change an otherwise completed repair or replace the original failure. `OperationAttempt<T>` exposes genuine successful DTOs or the adopted outer `OperationFailure`; absent evidence, persistence failure and measured mutation state remain explicit. Unsuccessful projection never fabricates an all-zero state or nine successful bindings.

## Materialization-boundary report

Generation plans contain the normalized/transformed states, actual helper results, source/revision/content bindings, explicit roles and artifacts, target/naming constraints and their complete diagnostic chains. `planArtifactEmission` checks the plan hash and every contained helper and diagnostic reference. It does not rerun the planner, query its constructor context for missing facts, or invent artifacts from local conventions. Rehashing a changed artifact does not bypass comparison with the plan's bound naming descriptions.

The native SDK returns abstract artifact values and an emission plan through the frozen Aeostara interface. The pinned base `specs/interfaces/IAshBindingProvider.pseudo.md`, Operations and Side-Effect Classification, expressly defines `planArtifactEmission -> ArtifactEmissionPlan` and side effects as `none`. Concrete filesystem/service/module materialization is not implemented by that interface. A downstream host claiming the complete canonical `ArtifactEmitter` responsibility must provide and verify the corresponding plan-only materializer; this SDK's pure emission-plan test does not establish that additional claim. Configuration recovery execution is a separate, scoped native capability and is not a substitute for generation artifact materialization.

| Topology range/schema | Depths 1 through 8 are supported. Depth zero has no genuine edges and cannot satisfy the frozen `TopologyPlan` edge minimum; it returns a diagnostic failure. | Host containment and safe halt | Canonical classes/categories and blocked-recovery transitions are evaluated. Ordinary configuration planning rejects unsupported containment/escalation/terminal host actions. A permanently stopped failed-restoration session preserves its lease and failure until teardown; it does not claim ASH `SAFE_HALT` or a platform halt. No approval of a new canonical recovery model is implied. |
| Concrete artifact materialization | The SDK implements the frozen abstract emission-plan interface. Concrete host artifact creation is outside that interface and is not claimed as verified canonical materialization. |
| Durability and deployment | The default target writer holds a checked exclusive handle and writes in place. Separate scoped atomic publication does not establish crash/power-loss durability. Representative hardware, storage and ACL/reboot tests remain deployment qualification. Ordinary static-package signing is not asserted. |

No local waiver changes a non-waivable ASH requirement. A boundary that prevents a required invariant or module contract from being satisfied must affect the acceptance judgment; calling it a caveat does not make it harmless. Unsupported context fails explicitly and is never silently replaced with a guessed semantic result.

## Acceptance judgment

The candidate native matrix above passed. Final exact-source acceptance of the selected Aeostara SDK binding remains pending at this document's preparation. That scope includes its frozen provider operations, consumed canonical semantics, required diagnostics and authorized native configuration realization. It does not claim a complete standalone canonical host runtime implementing concrete generation artifact materialization, platform containment or platform halt. The final independent review must name its scope explicitly and assess the observed boundaries before issuing its judgment.

This document makes no automatic `NON-CONFORMANT` judgment from a missing assertion trace and no `CONFORMANT` judgment from green native totals. Source proofs, executed properties and verified implementation boundaries must be assessed together. A passing scoped SDK review cannot be presented as full nine-module host acceptance.

Any judgment claiming complete canonical host conformance must use the pinned `implementation-acceptance.md` language: `CONFORMANT` only when all invariants pass, all five categories are covered, all module contracts are satisfied and diagnostics are complete; `CONFORMANT WITH CAVEATS` only when every acceptance condition holds and named caveats do not affect core conformance; otherwise `NON-CONFORMANT` with the unmet conditions, invariant/category IDs where applicable and remediation. There is no partial-conformance judgment. A selected SDK release judgment must instead identify its concrete interface and consumed-semantic scope, exact-source evidence and exclusions, without renaming that narrower result as full canonical host conformance. Publication and administrator bypass do not supply semantic acceptance or waive failed technical evidence.

## Windows decisions and resource constraints

The SDK uses native C++20, CMake, Visual Studio 2022 v143 MSVC 19.44.35223, VCToolsVersion 14.44.35207 and Windows SDK 10.0.26100.0 on Windows x64. Debug uses `/MDd`; Release uses `/MD`, with exceptions, RTTI and matching iterator-debug mode. Both installed configurations use the LEAN diagnostic backend and embedded `/Z7` information. Installed CMake metadata and native NuGet use relative paths; Windows `bcrypt` and `ole32` are transitive system libraries. There is no fetched runtime dependency package. CMake ZIP, native NuGet and developer-kit ZIP are prerelease assets under the repository's included Raven Forge dual license.

No measured latency/throughput target is asserted. Resource bounds constrain supported requests rather than authorize approximated semantics. `JsonLimits` permits 8 MiB raw and 16 MiB canonical per document, 32 source documents and 64 MiB complete-input raw aggregate, depth 64, 100,000 nodes and 1 MiB decoded strings. Diagnostic transport has the separate chain budget above; LEAN developer collection defaults to 64 events, 4 KiB per event, 256 KiB memory, one-hour retention and 2 MiB paired export. Limit exhaustion is explicit. Complete immutable semantic inputs and content-bound authorization configure behavior; ordinary configuration differences do not select a mapping profile, recovery target or policy.

Build/test instructions and deployment boundaries are documented in [BUILD_AND_TEST.md](BUILD_AND_TEST.md) and [SDK_GUIDE.md](SDK_GUIDE.md). Release qualification records must bind the exact clean source, compiled tuple, installed-consumer sources, tests, package hashes and independent judgment. The controlling operator instruction package and raw execution evidence remain outside product payloads.
